## Discussion

* **Goal success rate**: 9/9 runs (100%) reached the goal.
* **Bad states visited**: 0 across every run — the `+∞` edge cost for any
  transition into a bad state (Sec. 4 of the design report) makes this a
  hard guarantee, not a soft preference.
* **Cost vs. safety trade-off (TC3)**: the planner rejects the cheaper
  path (cost 3, hugging the bad state at distance ≈0.2) in favor of the
  costlier one (cost 6, `minDistToBad = 1.513`), because the proximity
  penalty (`λ_proximity / (dist + ε)`) dominates for the close path. This
  is directly tunable via `DStarLitePlanner::Weights`.
* **Replanning cost (TC4–TC6)**: `exploredStates` after each dynamic
  update (6, 5, 5) is comparable to — not a multiple of — a from-scratch
  solve on graphs of this size, consistent with the incremental-replan
  argument in the design report. On these toy graphs the absolute
  numbers are too small to show asymptotic savings; the design report's
  complexity analysis (Sec. 5) is the argument for why savings grow with
  graph size, since only vertices near the change become inconsistent.
* **Memory usage**: not separately instrumented (toy graphs are a few KB
  regardless); the design report's O(V+E) bound is the relevant claim for
  larger inputs. Re-run with `/usr/bin/time -v ./planner_demo` on a
  larger generated graph if a course deliverable requires a measured
  number.

## Reproducing

```bash
make

```
